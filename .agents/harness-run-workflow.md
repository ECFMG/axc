# Feature run workflow

Use this workflow for bounded feature implementation runs. It keeps comparisons reproducible while remaining applicable to different domains and feature sizes. It does not apply to explicitly requested harness maintenance or evaluation-file edits.

## Establish the run boundary

- Record the starting branch/commit and `git status --short`; preserve existing user changes. Read the fixed task requirements once and extract the allowed paths, acceptance criteria, and prohibited changes into a compact working checklist.
- Check required workspace dependency edges against existing package manifests before writing code. When the task permits adding dependencies with justification, that permission includes the root package-manager lockfile as the generated record of dependency declarations made in package manifests inside the allowed write boundary, unless the task explicitly prohibits lockfile changes. Explain each dependency edge before editing and keep the lockfile diff limited to those edges and unavoidable package-manager metadata. Obtain a boundary exception for root workspace configuration or unrelated lockfile changes. Do not introduce undeclared imports or flatten architecture to avoid package dependencies.
- Review any existing baseline verification record before implementation, including dependency advisories, Biome results, and Knip findings. If no comparable baseline record exists, run `pnpm run knip` before editing and record actionable findings separately from configuration hints. Do not change scan ignores or root `knip.json` merely to silence findings during a bounded feature task.
- Convert the task into a small evidence matrix before implementation. Classify each concept by domain identity and lifecycle as an aggregate root, child entity, value object, or derived projection, then map each required behavior and error to its owning layer, exact Cellix counterpart, public contract or documentation, and planned test. Treat a persisted business object with independent identity and lifecycle as an aggregate candidate even if this run exposes only queries. Use a derived projection classification only with evidence that it has no independent domain lifecycle; the absence of write endpoints is not that evidence. For each aggregate, identify its domain context, `getNewInstance` factory and valid initial state, props, entity reference, constrained value objects, exports, and focused tests before implementing a read repository. Record which command-side repository, unit-of-work, and adapter responsibilities are needed now and which are deferred until commands are requested. For every material rule, record the expected behavior, a plausible incorrect implementation the evidence must reject, and the exact observable outcome. For a persisted command workflow, include aggregate construction, transitions, constrained values, child lifecycle, a storage-record/domain-props adapter, a converter, repository creation and rehydration, unit-of-work wiring, and audit or history mapping. Map each to the corresponding `case/service-ticket-v1` persistence file and focused test before writing implementation code. For an HTTP API, include method and path, request validation, success response, status code, and specified error code. Mark rules that must hold when the application boundary is called directly. Do not add requirements that are absent from the task or repository instructions.
- When the repository has an HTTP acceptance suite, include its feature file and step definitions in the evidence matrix for each new or changed API workflow. Plan at least one scenario through the running application host for each affected endpoint, with the material success response and specified error status and code. Keep focused domain, service, persistence, and in-process HTTP tests as separate evidence.

## Use context and verification deliberately

- Use targeted file discovery and bounded reads. Read only the Cellix layers applicable to the chosen feature, including parent and sibling composition files, public exports, and test companions. Add reference paths, dependency decisions, justified omissions, and verification results to the working map. Update it only when a decision or result changes; reuse it for the Cellix review and final report instead of regenerating plans, tables, or whole repository diffs. Do not write run notes into an unauthorized repository path.
- Implement and test behavior at its owning layer. Add composed public-path coverage for the feature, but do not count that as the focused domain, application-service, or persistence test. For command aggregates, inspect the adapter/converter, repository, unit-of-work, and composition test companions independently; a unit-of-work-only test does not cover conversion or repository creation. If a custom adapter replaces the reference technology, identify the observable semantics being preserved and directly test the ones relevant to the task and risk, including record ↔ aggregate round trips, nested history mapping, commit, rollback, isolation or serialization, and defensive copying when implemented.
- Design evidence that distinguishes the intended behavior from plausible partial or incorrect implementations. Use positive cases, counterexamples, meaningful boundaries, failure-path effects, and precise state or output assertions as applicable. For each material rule, at least one test must change outcome if that rule is omitted, weakened, inverted, or applied in the wrong order. When several rules appear in one scenario, include independently discriminating data or focused cases so the combined scenario cannot hide which rule is working. For filters and other predicates, include a counterexample that satisfies the other relevant conditions but must be excluded by the predicate under test, and assert the complete expected result or ordered identifiers. Use targeted mutation testing or fault injection for high-risk rules when ordinary test inspection does not provide strong confidence; it is not required universally.
- Start with focused tests. After the final implementation change, run `pnpm run verify`; do not substitute only lint, typecheck, build, architecture tests, or unit tests for that gate. Resolve patch-introduced findings within the allowed boundary, including Biome formatting/import-order failures and Knip unused exports, then rerun the failed focused check and the full gate. Compare Knip configuration hints with the starting baseline. If an external security service is unavailable, follow the fallback in `AGENTS.md` and continue every non-external verification stage. Run shared build-dependent checks sequentially when diagnosing a failure; avoid simultaneous Turbo pipelines that mutate the same artifacts.
- Summarize successful commands briefly, distinguishing fresh execution from cache hits. Inspect and report detailed logs when needed to diagnose a failure or finding. Repeat a check only after relevant changes, a failure, or an environment correction; do not count sandbox startup failures as product defects when an authorized unchanged rerun passes.

## Review and finish

- Complete the Cellix review. Compare the actual tree with the planned tree and map every acceptance criterion to source, test, and documentation evidence where required. For every material rule, identify the plausible incorrect implementation rejected by its evidence; strengthen any test that would still pass if the rule were omitted, weakened, inverted, or incorrectly ordered. Verify semantic fidelity, not only matching folders: persisted business objects with independent identity and lifecycle have aggregate slices even if their current API only reads them; command workflows additionally use the applicable Cellix repository factory, adapter/converter, unit-of-work composition, and child-entity patterns, with focused tests at each owning layer. Compare persisted-field and nested-history round trips, not only HTTP responses or transaction outcomes. For specified errors, verify both status and error code; verify material response and audit fields rather than relying only on collection lengths. A derived projection needs an explicit ownership and lifecycle rationale, not merely a query endpoint.
- For an HTTP feature, inspect the acceptance-suite diff and run its focused command against the application host. If no acceptance scenario was added or updated, record why existing scenarios already cover every changed public workflow; a passing healthcheck alone is not feature acceptance evidence.
- Audit public mutations independently of transport: exercise invalid business inputs directly and assert that rejected operations leave state unchanged. Check boundary values and use distinguishable data for each required behavior.
- Before handoff, inspect the final Knip output. Patch-introduced unused files, dependencies, exports, or exported types must be resolved in code. Keep baseline-only configuration hints separate and do not edit root Knip configuration to hide them.
- Inspect `git diff --name-status`, `git diff --cached --name-status`, and `git ls-files --others --exclude-standard` against the initial snapshot and exact allowed paths. Check prohibited changes within allowed directories too: authentication, production settings, deployment, and unrelated behavior remain protected. Resolve agent-created violations; do not discard user changes.
- Run `git diff --check` and `git diff --cached --check`. Preserve the patch without automatically staging or committing it. Never bypass a failed hook to finish a feature run.
- Follow the task's explicit reporting requirements. Do not invent dollar cost, usage, or vendor approval evidence.

## Preparing the next comparable run

Before a comparative run, prepare one shared baseline with synchronized dependencies and recorded results for the checks required by `AGENTS.md` and the task. Remediate baseline dependency issues in a separate authorized maintenance change, then use the same starting point for every comparison. If a fixed task permits a controlled seed, it may reduce repeated setup work; record its commit and use it consistently across the comparison. Keep runs from different starting points in separate comparisons. Keep security commands and policy consistent. Record temporary service outages as external verification limitations and rerun the unchanged scan when service recovers; do not score them as generated-code or harness defects.

When the harness exposes usage snapshots, record them at meaningful phase boundaries and calculate phase usage from successive snapshots. Include input, cached input, output, and reasoning tokens when available. Mark missing data as unavailable rather than estimating it. Compare usage and quality only across runs with the same task, starting point, verification policy, and measurement method.

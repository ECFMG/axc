# Enrollment request API

The sample API lets learners submit requests and operators review them. All timestamps are ISO 8601 UTC strings. Request IDs are opaque strings generated by the server. Data lasts for the local API process; restarting creates a fresh sample catalog and clears enrollment requests. See the [storage decision](../adr/0001-training-workflow-storage.md).

## Create a request

`POST /api/enrollment-requests`

```json
{
  "courseId": "course-001",
  "learnerEmail": "learner@example.org",
  "justification": "I need this course to prepare for upcoming secure development work."
}
```

The course must exist and be active. Email must be valid; it is trimmed and lowercased for storage, duplicate checks, and list filters. Justification must contain 20–500 characters, inclusive. The server controls status, IDs, timestamps, and history. A learner can have one pending or approved request per course. Rejected or cancelled requests allow a new submission. Different learners or courses can have separate active requests. A database constraint also prevents simultaneous duplicate submissions.

Successful response: **201**.

```json
{
  "id": "enroll-71fc6420-b1ec-41d8-a150-611d871ee1b4",
  "courseId": "course-001",
  "learnerEmail": "learner@example.org",
  "justification": "I need this course to prepare for upcoming secure development work.",
  "status": "pending",
  "createdAt": "2026-06-27T10:00:00.000Z",
  "updatedAt": "2026-06-27T10:00:00.000Z",
  "statusHistory": [
    {
      "fromStatus": null,
      "toStatus": "pending",
      "changedAt": "2026-06-27T10:00:00.000Z",
      "changedBy": "system",
      "reason": null
    }
  ]
}
```

## Retrieve a request

`GET /api/enrollment-requests/:id` returns **200** with the full request object shown above, including all history entries. Unknown IDs return **404**.

## List requests

`GET /api/enrollment-requests?status=pending&courseId=course-001&learnerEmail=learner@example.org`

All filters are optional and combine with AND. `status` accepts `pending`, `approved`, `rejected`, or `cancelled`. `courseId` matches exactly; `learnerEmail` matches the normalized email exactly. Whitespace-only optional filters count as absent. Invalid status or email filters return **400**. Results are ordered by creation time, then request ID.

Successful response: **200**, `{ "items": [ ... ] }`, where each item is the complete request object. No matches return `{ "items": [] }`. This endpoint has no pagination requirement and returns all matches.

## Change status

`PATCH /api/enrollment-requests/:id/status`

Approval:

```json
{ "status": "approved", "changedBy": "reviewer@example.org" }
```

Rejection:

```json
{
  "status": "rejected",
  "changedBy": "reviewer@example.org",
  "reason": "Learner has not completed the prerequisite course."
}
```

| Current status | Allowed next status |
| --- | --- |
| `pending` | `approved`, `rejected`, `cancelled` |
| `approved` | `cancelled` |
| `rejected` | None |
| `cancelled` | None |

Repeated transitions to the same status return **409**. `changedBy` must be a non-empty operator identifier. Rejection requires a non-empty reason; other changes may include a reason. Empty optional reasons count as absent. No authentication is added by this sample: `changedBy` is client supplied and is not a verified identity.

Successful response: **200** with the complete updated request. Changing status updates `updatedAt` and appends one history entry atomically. For example, the approval adds:

```json
{
  "fromStatus": "pending",
  "toStatus": "approved",
  "changedAt": "2026-06-27T11:00:00.000Z",
  "changedBy": "reviewer@example.org",
  "reason": null
}
```

Failed operations preserve the request and its history. Concurrent updates use transactions so they cannot overwrite audit entries.

## Errors

Every error uses this envelope; details are field-specific and contain no stack traces, database messages, or internal identifiers:

```json
{
  "error": {
    "code": "INVALID_REQUEST",
    "message": "The request could not be completed.",
    "details": [{ "field": "justification", "message": "justification must be between 20 and 500 characters." }]
  }
}
```

| Condition | HTTP status | Code |
| --- | --- | --- |
| Invalid JSON, non-object body, missing or invalid fields, invalid list filter | 400 | `INVALID_REQUEST` |
| Missing course | 404 | `COURSE_NOT_FOUND` |
| Draft or retired course | 409 | `COURSE_NOT_ACTIVE` |
| Duplicate pending or approved request | 409 | `DUPLICATE_ACTIVE_REQUEST` |
| Request not found for GET or PATCH | 404 | `ENROLLMENT_REQUEST_NOT_FOUND` |
| Unknown status value | 400 | `INVALID_REQUEST` |
| Unsupported transition, including a no-op | 409 | `INVALID_STATUS_TRANSITION` |
| Missing or blank rejection reason / operator | 400 | `INVALID_REQUEST` |
| Unexpected server failure | 500 | `INTERNAL_ERROR` |

Unexpected failures use a generic message and empty details array; full errors are logged server-side. Course search query errors use `INVALID_QUERY_PARAMETER`, as documented in [course search](courses.md).
